# Учебный план «Git для командной разработки» (на примере приложения «Заметки»)

### Введение

Курс построен на **одном проекте** — консольном менеджере заметок на Python. В каждом модуле ученик добавляет новую функциональность, одновременно осваивая Git.  
**Важно:** все Git-команды даются явно, с пояснениями. Код для фич ученик пишет **сам**, без готовых решений (если только не попросит подсказку).  

---

### Правила хорошего тона (общий раздел)

С самого начала курса ученик должен придерживаться следующих стандартов. Они будут повторяться и закрепляться в каждом модуле.

1. **Сообщения коммитов** – по формату Conventional Commits:  
   `<тип>: <краткое описание в настоящем времени>`  
   Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `chore`, `test`, `ci`.  
   Пример: `feat: add search command`.

2. **Именование веток** – использовать префиксы:  
   `feat/`, `fix/`, `hotfix/`, `chore/`, `docs/`.

3. **Все изменения в `main` – только через Pull Request** (кроме самых первых коммитов в одиночном проекте, но привычка должна быть сформирована сразу).

4. **Перед коммитом** – всегда проверять `git status`, чтобы случайно не добавить лишние файлы.

5. **Ветки после слияния удалять** – локально и на GitHub.

6. **Для общих веток использовать только `merge`, для личных – разрешён `rebase`** (с осторожностью).

### Основной курс (обязательные модули)

#### Модуль 1. Подготовка, SSH, удалённый репозиторий и первый пуш

**Цель:** Настроить окружение, создать репозиторий на GitHub, настроить SSH, выполнить первый коммит и пуш.

**Задания:**
1. Зарегистрироваться на GitHub (если нет).
2. Сгенерировать SSH-ключ (`ssh-keygen -t ed25519 -C "..."`), добавить публичный ключ в настройки GitHub.
3. Включить приватность email в GitHub, скопировать анонимный адрес (вида `12345678+username@users.noreply.github.com`).
4. Настроить глобальные `user.name` и `user.email` (использовать анонимный адрес).
5. Создать локальную папку проекта, инициализировать Git (`git init`).
6. Создать `README.md`, сделать первый коммит (`git add`, `git commit -m "docs: initial project structure"`).
7. Создать пустой репозиторий на GitHub (без README, .gitignore и лицензии).
8. Связать локальный репозиторий с удалённым (`git remote add origin <SSH-URL>`) и запушить (`git push -u origin main`).
9. Проверить, что на GitHub появились файлы.

**Правила/стандарты, отрабатываемые здесь:**
- Первый коммит оформлен как `docs:` – изменение документации.
- Ветка называется `main` (при создании репозитория ветка может называться `master`. Объяснить, что `main` сейчас является стандартом и лучше использовать его).

**Проверка:** ученик присылает вывод `git remote -v`, `git log --oneline` и ссылку на репозиторий.

#### Модуль 2. Основы: статус, добавление, коммит, игнорирование файлов

**Цель:** Научиться базовым командам и работе с `.gitignore`.

**Задания:**
1. Создать файл `notes.py` (пока пустой) и сделать коммит.
2. Создать файл `.gitignore` в корне, добавить в него `notes.json`, `__pycache__/`, `*.pyc`, `venv/`.
3. Проверить, что игнорирование работает (`git status` не показывает эти файлы).
4. Создать виртуальное окружение Python (`python -m venv venv`) и убедиться, что оно не отслеживается.
5. Добавить `.gitignore` в репозиторий и закоммитить.

**Правила/стандарты, отрабатываемые здесь:**
- Сообщение коммита для `.gitignore` – `chore: add .gitignore`.
- Использование `git status` перед каждым коммитом.

**Проверка:** ученик присылает содержимое `.gitignore` и вывод `git status` после создания venv.

#### Модуль 3. Первая фича: команды `add` и `list`

**Цель:** Написать рабочий код и закрепить навыки коммитов.

**Задания:**
1. Реализовать в `notes.py`:
   - Функции `load_notes()` и `save_notes(notes)` для работы с JSON.
   - `add_note(title, text)` – сохраняет заметку с полями `id`, `title`, `text`, `created_at`, `tags`.
   - `list_notes()` – выводит все заметки в читаемом виде.
   - CLI (через `sys.argv`) с командами `add` и `list`.
2. Сделать несколько коммитов (например, один для структуры, один для CLI, один для сохранения).
3. Проверить программу: добавить заметки и вывести список.

**Правила/стандарты, отрабатываемые здесь:**
- Первый коммит фичи – `feat: add note storage and CLI`.
- Второй коммит – `feat: implement add and list commands`.
- Сообщения в настоящем времени.

**Проверка:** ученик присылает код `notes.py` и скриншот/текст выполнения команд:
```
python notes.py add "Первая" "Привет"
python notes.py list
```

#### Модуль 4. Ветки: создание и переключение

**Цель:** Освоить работу с ветками.

**Задания:**
1. Создать ветку `feat/tags` от `main` (`git checkout -b feat/tags`).
2. В этой ветке добавить в структуру заметки поле `tags` (список строк) и функцию `add_tag(note_id, tag)` (пока без сохранения, просто добавление в список).
3. Изменить `list_notes()` так, чтобы выводились теги.
4. Сделать коммиты в этой ветке (не менее двух).
5. Переключиться на `main` и убедиться, что код остался без тегов.
6. Показать граф веток (`git log --oneline --graph --all`).

**Правила/стандарты, отрабатываемые здесь:**
- Именование ветки `feat/tags`.
- Коммиты: `feat: add tags field`, `feat: display tags in list`.
- Проверка, что изменения изолированы в ветке.

**Проверка:** ученик присылает вывод `git branch` и `git log --oneline --graph --all`.

#### Модуль 5. Слияние и разрешение конфликтов (параллельные ветки)

**Цель:** Научиться создавать конфликт и разрешать его вручную.

**Задания:**
1. Убедиться, что ты на `main` (и все изменения из `feat/tags` ещё не влиты).
2. Создать ветку `feat/search` от `main` (`git checkout -b feat/search`).
   - Реализовать команду `search` (поиск по тексту заметок): добавить функцию `search_notes(keyword)`, интегрировать в CLI.
   - **Добавить описание команды `search` в `print_help()`** (например, в конец блока).
   - Сделать коммит.
3. Переключиться на `main` и создать ветку `feat/sort` от `main` (`git checkout -b feat/sort`).
   - Реализовать команду `sort` (сортировка по дате).
   - **Изменить `print_help()`** – переставить строки или изменить формулировки так, чтобы они конфликтовали с изменениями из `feat/search` (например, разместить описание `sort` в том же месте, где в `feat/search` добавлено описание `search`).
   - Сделать коммит.
4. **Сначала** слить `feat/search` в `main` (без конфликта, так как изменения не пересекаются).
5. **Затем** слить `feat/sort` в `main` – возникнет конфликт в `print_help()`.
6. Разрешить конфликт вручную: оставить все команды (`search`, `sort` и уже существующие).
7. Завершить слияние (`git add`, `git commit`).
8. Показать итоговый граф.

**Правила/стандарты, отрабатываемые здесь:**
- Создание параллельных веток от одного коммита (объяснить, что это делается только для имитации параллельной работы в команде).
- В реальности для уменьшения конфликтов при будущем вливании в общую ветку, периодически вливают изменения из общей ветки в фича-ветку, чтобы заранее решить все конфликты (это описано в разделе 7 «Правил хорошего тона»).
- Разрешение конфликта – объяснить, как выбирать нужный код.
- Merge-коммит с пояснением (например, `Merge branch 'feat/sort' with conflict resolution`).

**Проверка:** ученик присылает:
- Код `print_help()` после разрешения конфликта.
- Скриншот/текст `git log --oneline --graph`.
- Вывод `python notes.py search` и `python notes.py sort` (работают).

#### Модуль 6. Удалённая работа и Pull Request (раннее введение)

**Цель:** Освоить процесс создания PR, ревью и слияния на GitHub.

**Задания:**
1. Создать ветку `feat/stats` от `main` (`git checkout -b feat/stats`).
2. Реализовать команду `stats` (выводит общее количество заметок и количество заметок с тегами).
3. Сделать коммит и запушь ветку на GitHub (`git push -u origin feat/stats`).
4. На GitHub открыть Pull Request из `feat/stats` в `main`.
   - Заполнить описание: что сделано, пример использования, чек-лист (проверено локально, код добавлен, справка обновлена).
5. **Намеренно создать конфликт:** изменить `print_help()` в `main` через интерфейс GitHub (отредактировать файл прямо на GitHub, сделать коммит в `main`).
6. Обновить ветку `feat/stats` (сделать `git merge main` или `rebase`), разрешить конфликт, запушить обновление (PR автоматически обновится).
7. После успешного прохождения ревью (можно самому себе) смержить PR через интерфейс GitHub.
8. Удалить ветку на GitHub и локально.

**Правила/стандарты, отрабатываемые здесь:**
- Весь процесс PR – это стандарт для любой фичи.
- Draft PR для незавершённой работы (показываем, как переключить на Ready for review).
- Использование `--force-with-lease` при обновлении ветки после rebase (если использовали rebase).

**Проверка:** ученик присылает ссылку на PR (или скриншоты процесса), а также код `stats` и вывод `git branch -d feat/stats`.

#### Модуль 7. Теги (маркеры релизов)

**Цель:** Научиться отмечать стабильные версии.

**Задания:**
1. Поставить тег на текущий `main` (`git tag -a v1.0.0 -m "First stable release with add, list, search, sort, tags, stats"`).
2. Отправить тег на GitHub (`git push origin --tags`).
3. Проверить, что тег появился в разделе Releases на GitHub.

**Правила/стандарты, отрабатываемые здесь:**
- Тег – аннотированный, с осмысленным сообщением.
- Семантическое версионирование (v1.0.0).

**Проверка:** ученик присылает вывод `git tag` и ссылку на тег на GitHub.

#### Модуль 8. Исправление и откаты (с контекстом)

**Цель:** Научиться исправлять локальные и опубликованные изменения.

**Задания (сценарий):**
1. В новой ветке `practice/fix` (или прямо в `feat/...`) намеренно внести баг: например, неправильно считать количество заметок в `stats`. Закоммитить и запушить.
2. «Обнаружить» баг. Если коммит ещё не запушен – исправить через `git commit --amend` (добавить изменения в последний коммит или изменить сообщение).
3. Если коммит уже запушен – использовать `git revert <хеш>` для создания коммита-отмены.
4. Создать ещё один баг (например, забыли добавить файл в коммит) и исправить через `amend` с добавлением файла.
5. Использовать `git reset --soft HEAD~1` для отката последнего локального коммита, но с сохранением изменений.
6. Использовать `git reset --hard` на тестовой ветке (не на `main`) и восстановить потерянный коммит через `git reflog`.

**Правила/стандарты, отрабатываемые здесь:**
- Для опубликованных изменений – только `revert`.
- Для локальных – можно `reset` с осторожностью.
- Понимание разницы между `--soft`, `--mixed`, `--hard`.

**Проверка:** ученик присылает описание каждого шага, а также вывод `git log` до и после `revert` и `reflog`.

#### Модуль 9. Rebase (интерактивный и обычный)

**Цель:** Научиться делать историю линейной и чистой.

**Задания:**
1. Создать ветку `practice/rebase` от `main`.
2. Внести три изменения (каждое – отдельным коммитом): например, добавить комментарий в начале файла, изменить справку, добавить пустую строку в конце.
3. Сделать интерактивный rebase для трёх последних коммитов (`git rebase -i HEAD~3`) и объединить их в один (squash).
4. Обновить ветку из `main` через `git rebase main` (если `main` изменился).
5. Запушить с `--force-with-lease` (если ветка уже была на GitHub) и создать PR (по желанию).

**Правила/стандарты, отрабатываемые здесь:**
- Использование `squash` для объединения «мусорных» коммитов.
- Правильное оформление итогового сообщения коммита.
- Применение `--force-with-lease` вместо `--force`.

**Проверка:** ученик присылает:
- `git log --oneline` до и после rebase.
- Сообщение объединённого коммита.

#### Модуль 10. Сравнение merge и rebase (стратегии)

**Цель:** Понять, когда использовать merge, а когда rebase, и выбрать стратегию для проекта.

**Задания:**
1. Прочитать краткое сравнение:
   - `merge` – для общих веток, сохраняет историю ветвления, безопасен.
   - `rebase` – для личных веток, делает историю линейной, но переписывает коммиты.
2. На практике: обновить свою фича-ветку через `git rebase main`, затем создать PR и смержить через `merge` (или через интерфейс GitHub).
3. Написать в `README.md` (или отдельном файле) краткое обоснование: какая стратегия принята в этом проекте и почему.

**Правила/стандарты, отрабатываемые здесь:**
- Закрепление понимания, что rebase – это инструмент для личных веток, а merge – для общих.

**Проверка:** ученик присылает текст в `README.md` с описанием стратегии.

### Дополнительные модули (по желанию, для углублённого изучения)

Эти модули можно пройти после основного курса, если есть время и интерес.

#### Модуль Д1. Stash (временное сохранение)

**Цель:** Научиться прятать незакоммиченные изменения при переключении задач.

**Задания:**
1. Внести изменения в `notes.py` (например, добавить комментарий), но не коммитить.
2. Переключиться на другую ветку – Git попросит закоммитить или спрятать.
3. Использовать `git stash push -m "WIP: experimenting"`.
4. Переключиться на ветку, сделать что-то, вернуться обратно.
5. Применить стэш (`git stash pop`) и убедиться, что изменения вернулись.
6. Показать, что стэш удалился из списка.

---

#### Модуль Д2. Git Hooks (автоматизация)

**Цель:** Настроить автоматическую проверку синтаксиса перед коммитом.

**Задания:**
1. Создать `pre-commit` хук в `.git/hooks/pre-commit`.
2. Написать скрипт, проверяющий синтаксис `notes.py` (`python -m py_compile notes.py`).
3. Сделать его исполняемым.
4. Внести синтаксическую ошибку, попробовать закоммитить – хук должен заблокировать.
5. Исправить ошибку и убедиться, что коммит проходит.

---

#### Модуль Д3. Bisect (поиск коммита с багом)

**Цель:** Научиться находить коммит, который внёс ошибку.

**Задания:**
1. На ветке `main` намеренно внести баг (например, сломать `add_note`) и закоммитить.
2. Сделать ещё несколько коммитов (исправления в справке, форматирование).
3. Запустить `git bisect start`, указать `bad HEAD` и `good <коммит_до_бага>`.
4. Поочерёдно переключаться между коммитами, тестировать программу, помечать `good`/`bad`.
5. Найти коммит с багом, исправить баг.
6. Завершить `git bisect reset`.
