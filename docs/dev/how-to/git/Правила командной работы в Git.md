# Правила  командной работы в Git

Этот документ содержит рекомендации, которые помогут избежать конфликтов, сохранить историю чистой и облегчить работу коллегам.

Соблюдение этих правил — признак профессионализма и уважения к команде.

---

## 1. Всегда проверяйте `git status` перед коммитом

Перед тем как сделать коммит, выполните:
```bash
git status
```
Убедитесь, что в коммит попадают только нужные файлы. Если вы видите лишние (логи, временные файлы, настройки IDE), добавьте их в `.gitignore`.

---

## 2. Используйте `.gitignore` с самого начала

Добавьте в `.gitignore` всё, что не должно храниться в репозитории:
- Сгенерированные файлы (`notes.json`, `*.log`, `__pycache__/`)
- Файлы окружения (`.env`, `venv/`, `*.pyc`)
- Временные файлы редакторов (`.vscode/`, `.idea/`, `*.swp`)

**Пример минимального `.gitignore` для Python:**
```gitignore
__pycache__/
*.pyc
venv/
.env
notes.json
*.log
```

---

## 3. Не коммитьте большие бинарные файлы

Git плохо справляется с бинарными файлами (изображения, видео, архивы). Они раздувают историю и замедляют клонирование.  
Используйте:
- **Git LFS** (Large File Storage) для обязательных бинарников.
- Внешние хранилища (S3, Google Drive) для всего остального.

**Примечание**: в нашем проекте будет просто файл со списком бинарников и ссылки на них

---

## 4. Пишите осмысленные сообщения коммитов

Следуйте **Conventional Commits** – это стандарт, принятый в тысячах проектов.

**Формат:**
```
<тип>(<контекст>): <краткое описание в настоящем времени>
```

**Типы:**
- `feat` – новая фича
- `fix` – исправление бага
- `docs` – документация
- `style` – форматирование (не меняет логику)
- `refactor` – улучшение кода без изменения поведения
- `chore` – технические задачи (зависимости, настройки)
- `test` – добавление/исправление тестов
- `ci` – настройка CI/CD

Примечание: в <контекст> возможно будем писать, какой модуль был изменен. А может просто опустим эту фигню и не будем указывать

**Примеры:**
```
feat: add search command
fix: correct ID generation for new notes
refactor: unify note printing
chore: add .gitignore
```

**Описание должно быть:**
- кратким (до 50 символов)
- в настоящем времени («добавить», «исправить», а не «добавил», «исправил»)

---

## 5. Не пушите напрямую в `main`

Все изменения должны проходить через **Pull Request** (PR) на GitHub.

Это обязательное условие для:
- Код-ревью
- Обсуждения архитектуры
- Автоматических проверок (CI)

Если вы работаете один – это правило можно смягчить, но **для командной работы оно *обязательно***.

---

## 6. Используйте Draft PR для незавершённой работы

Если задача ещё не доделана, но вы хотите показать коллегам подход или запустить тесты – откройте PR как **Draft** (черновик).  
В этом статусе:
- PR нельзя случайно смержить
- Ревьюеры не получают уведомлений
- Вы можете обновлять его без давления

Когда работа готова, нажмите **Ready for review**.

---

## 7. Регулярно обновляйте свою ветку из `main`

Чтобы избежать больших конфликтов в момент слияния, периодически подтягивайте изменения из `main` в свою ветку:

```bash
git checkout main
git pull origin main
git checkout feature/my-feature
git merge main
```


Или используйте `rebase` чтобы не создавать merge-коммит, объединить слишком мелкие коммиты и заранее решить конфликты перед вливанием в `main` (если вы уверены, что никто не работает с вашей веткой):
```bash
git fetch origin # загружаем новые изменения
git checkout feature/my-feature # мы должны быть в своей ветке
git rebase origin/main # переносим свои коммиты поверх свежего main
```

**Примечание**: если вливаешь в `main` или другую общую ветку, то ***только*** `merge`,  В ветках где ты работаешь один можешь делать что хочешь.

---

## 8. Не используйте `git push --force` на общих ветках

Если нужно переписать историю в своей **личной** фича-ветке, используйте безопасную альтернативу:

```bash
git push --force-with-lease
```

Этот флаг проверит, что удалённая ветка не была обновлена кем-то другим во время вашей работы.

**Никогда не делайте `--force` на `main` или другие общие ветки!** Это ломает историю у всех разработчиков.

---

## 9. Удаляйте ветки после слияния

После того как PR влит в `main`, удалите ветку:
- На GitHub – кнопка «Delete branch» в интерфейсе PR
- Локально: `git branch -d feature/my-feature`
- На удалённом: `git push origin --delete feature/my-feature`

Это поддерживает репозиторий в чистоте и упрощает навигацию.

---

## 10. Осторожно с `git reset --hard`

Эта команда **удаляет изменения без возможности восстановления** (кроме как через `reflog`).  
Используйте её только если вы абсолютно уверены, что эти изменения больше не понадобятся.

Для безопасного отката:
- Если коммит ещё не запушен – используйте `git reset --soft` или `--mixed`.
- Если коммит уже запушен – используйте `git revert`, чтобы создать новый коммит с отменой.

---

## 11. Комментируйте сложные моменты в сообщениях merge-коммитов

Если вы разрешали конфликт или делали нестандартное слияние, добавьте пояснение в тело merge-коммита (не только в заголовок).  
Это поможет коллегам понять, почему код выглядит именно так.

---

## 12. Держите Pull Request небольшими и сфокусированными

Один PR должен решать **одну логическую задачу**.  
Слишком большой PR (более 300–500 строк изменений) сложно ревьюить, и в нём легко пропустить ошибку.  
Если задача большая – разбейте её на несколько последовательных PR.

---

## 13. Используйте `git stash` для переключения задач

Если вы начали править код, но нужно срочно переключиться на другую ветку (например, починить баг в продакшене), а коммит делать рано – временно спрячьте изменения:

```bash
git stash push -m "WIP: описание изменений"
```

Когда вернётесь – примените стэш обратно:
```bash
git stash pop
```

---

## 14. Настройте Git Hooks для автоматических проверок

Даже простой `pre-commit` хук, проверяющий синтаксис, спасёт от попадания «сломанного» кода в репозиторий.  
Это особенно важно в команде, где несколько человек могут случайно закоммитить неработающий код.

**Пример хука:**
```bash
#!/bin/bash
python -m py_compile notes.py || { echo "Syntax error!"; exit 1; }
```

**Примечание**: папку с готовыми хуками и инструкцию по их установке я размещу в репозитоии

---

## 15. Всегда делайте `git pull` перед началом работы

Перед созданием новой ветки или внесением изменений обновите локальный `main`:

```bash
git checkout main
git pull origin main
```

Это снижает риск конфликтов и гарантирует, что вы работаете с актуальной версией кода.

---

## 16. Знайте, как откатить опубликованные изменения

Если баг попал в `main` и уже запушен:
- ***НЕ* используйте** `git reset`
- Используйте `git revert <commit>`, чтобы создать новый коммит, который отменяет изменения старого

Это безопасно для всех разработчиков, так как не переписывает историю.

---

## 17. Соблюдайте правила именования веток

Используйте префиксы, чтобы сразу было понятно, над чем идёт работа:
- `feat/` – новая функциональность
- `fix/` – исправление бага
- `hotfix/` – срочное исправление в продакшене
- `chore/` – техническая задача
- `docs/` – обновление документации

Пример: `feature/add-stats`, `fix/login-error`.

---

## 18. Уважайте код-ревью

- Отвечайте на комментарии конструктивно.
- Если вы не согласны – аргументируйте.
- Вносите правки, если они обоснованы.
- Не сливайте PR, пока не разрешены все обсуждения.

Примечание: хз как будет у нас, разберемся на месте)

---

## 19. Ведите историю чисто

- Не создавайте коммиты типа "fix bug", "typo", "wip" – их стоит объединять в осмысленные коммиты (через `rebase -i` или `squash` при слиянии PR).
- Ветка перед PR должна содержать логически завершённые коммиты, а не хаотичную историю разработки.

---

## 20. Помните о безопасности

- Не храните пароли, токены, ключи в коде или в истории коммитов.
- Если секрет попал в репозиторий – немедленно смените его и используйте `git filter-repo` или инструменты для удаления из истории.

---

Соблюдение этих правил сделает работу в команде комфортной и предсказуемой.

**Помните: Git — это инструмент, и от того, как вы его используете, зависит здоровье всего проекта.**
