# Уточнения архитектуры

**Версия:** 3

Этот документ фиксирует архитектурные решения, которые были отдельно уточнены после первоначального описания системы.

При противоречии между этим документом и более ранними описаниями приоритет имеют решения, зафиксированные здесь.

## Vision и камеры

### Фиксированные роли камер

В системе используются три камеры с постоянными ролями:

- `overview` — обзорная камера;
- `stereo_left` — левая камера стереопары;
- `stereo_right` — правая камера стереопары.

Роли камер не меняются во время работы программы.

### Отдельный pipeline для каждой камеры

Каждая камера имеет собственный pipeline обработки:

- получение кадра;
- Detector;
- Tracker;
- формирование результата наблюдения.

Каждый camera pipeline выполняется в собственном прикладном потоке.

GStreamer может использовать свои внутренние служебные потоки для приёма и декодирования видеопотока. Поэтому Detector и Tracker не должны блокировать сам сетевой приём.

Старые кадры для обработки не накапливаются. Если pipeline не успел обработать предыдущий кадр, следующим берётся самый актуальный доступный кадр.

### Общего Vision Pipeline больше нет

Отдельный общий `Vision Pipeline`, через который последовательно проходили кадры всех камер, больше не используется.

Каждая камера обрабатывается независимо в своём pipeline.

### Camera Manager удалён

`Camera Manager` как отдельный архитектурный компонент удаляется.

Его роль передаётся объекту модуля `Vision`.

`Vision` владеет тремя camera pipeline:

- `overview`;
- `stereo_left`;
- `stereo_right`.

При необходимости внутри `Vision` может использоваться обычный registry или словарь камер, но это не отдельный архитектурный компонент.

## Stereo / Distance Provider

### Один общий компонент

Для определения дальности используется один общий компонент `Stereo / Distance Provider`.

Он работает с заранее заданной стереопарой:

- `stereo_left`;
- `stereo_right`.

### Аппаратная синхронизация

Левая и правая камеры аппаратно синхронизированы.

На обе камеры одновременно приходит общий сигнал съёмки, поэтому кадры стереопары физически снимаются в один и тот же момент.

### capture_id и receive_timestamp

Для сопоставления кадров стереопары используются:

- `capture_id` — основной идентификатор пары кадров;
- `receive_timestamp` — локальное время получения кадра на стороне приложения.

`capture_id` используется для стереосопоставления.

`receive_timestamp` используется для:

- диагностики;
- определения задержки;
- `stale_timeout`.

Для ожидания второго кадра стереопары допускается небольшой ограниченный буфер. Он нужен только для сопоставления кадров с одинаковым `capture_id`, а не для последовательной обработки старых кадров.

### Расчёт дальности

Дальность рассчитывается только для выбранного объекта на `stereo_left`.

`Stereo / Distance Provider` получает:

- кадр `stereo_left`;
- соответствующий ему кадр `stereo_right` с тем же `capture_id`;
- рамку выбранного объекта на `stereo_left`.

Источники дальности на текущем этапе:

- `stereo`;
- `manual`.

В будущем могут быть добавлены другие источники, например лидар.


### Поток выполнения Stereo

`Stereo / Distance Provider` выполняется в прикладном потоке `stereo_left`.

После обработки левого кадра Detector и Tracker поток `stereo_left` передаёт в `Stereo / Distance Provider`:

- левый кадр;
- рамку выбранного объекта;
- `capture_id`.

Соответствующий правый кадр с тем же `capture_id` берётся из небольшого ограниченного буфера кадров `stereo_right`.

На текущем этапе отдельный поток Stereo не создаётся.

При этом `Stereo / Distance Provider` должен оставаться отдельным классом с явным интерфейсом, чтобы в будущем, если стереорасчёт окажется слишком тяжёлым и начнёт заметно снижать частоту обработки `stereo_left`, его можно было вынести в отдельный worker без изменения интерфейса остальных модулей.

Возможная высокая вычислительная стоимость Stereo заранее учитывается, но решение о выделении отдельного потока будет приниматься после измерений на реальной реализации.

## Выбор целей

На текущем этапе объекты на `overview` и `stereo_left` выбираются независимо.

Автоматического сопоставления объектов между обзорной и левой стереокамерой пока нет.

Для хранения выбора используется структура по источникам:

```text
selected_targets:
    overview: 7
    stereo_left: 4
```

То есть ID всегда рассматривается вместе с источником, к которому он относится.

Правая камера `stereo_right` не имеет отдельного пользовательского выбора цели.

В будущем может быть добавлен отдельный механизм сопоставления объектов между `overview` и `stereo_left`.

## Режим «Ближайшая»

Режим автоматического выбора ближайшего объекта откладывается.

На текущем этапе он не входит в обязательную архитектуру.

## UI

### Основное отображение

В обычном режиме интерфейс показывает:

- `overview`;
- `stereo_left`.

Для обеих камер отображаются:

- обработанный кадр;
- рамки объектов;
- ID объектов;
- дополнительная информация рядом с объектом, состав которой будет определён позже.

### Правая камера

`stereo_right` в обычном интерфейсе не отображается.

Она используется в основном для стереозрения.

Её отображение может быть включено отдельно в диагностическом режиме через настройки.

### Отображаемый кадр

На текущем этапе UI показывает именно тот обработанный кадр, для которого получен соответствующий результат Vision.

Это позволяет гарантировать совпадение рамок объектов с изображением.

В будущем допускается переход на отображение самого свежего live-кадра, если контракты данных будут содержать достаточную информацию для корректной синхронизации результатов.

## Потоки

На текущем этапе прикладная модель потоков меняется относительно старого описания.

Используются:

- главный поток приложения:
  - UI;
  - Core;
  - Config Manager;
  - Supervisor;
- отдельный поток `overview`;
- отдельный поток `stereo_left`;
- отдельный поток `stereo_right`;
- отдельный поток Turret.

Отдельного общего потока Vision Pipeline больше нет.

Внутренние служебные потоки библиотек GStreamer, OpenCV, Qt и других зависимостей не относятся к прикладной модели потоков.

## Turret

Turret не знает своего абсолютного положения.

Он поддерживает два основных типа управления:

- относительное перемещение по двум осям;
- задание скорости вращения по двум осям.

Команда скорости содержит два значения:

- `speed_x`;
- `speed_y`.

### Очередь команд прототипа

На этапе прототипа все обычные команды Core → Turret передаются через одну FIFO-очередь и выполняются последовательно, одна за другой.

К обычным командам относятся, в частности:

- `MoveRelative`;
- `SetVelocity`;
- обычный `STOP`;
- команды калибровки;
- другие штатные команды Turret.

На этапе прототипа отдельный latest-only канал для `SetVelocity` не вводится.

Если позднее обычная FIFO начнёт создавать заметную задержку для команд скорости, семантика `SetVelocity` может быть пересмотрена отдельно.

### Обычный STOP

На уровне Core → Turret обычный `STOP` является обычной FIFO-командой.

Когда она доходит до Turret Controller, через HAL в STM32 отправляется стандартная UART-команда `STOP`.

После этого следующие команды, уже находящиеся в FIFO, продолжают выполняться в обычном порядке.

### Аварийный STOP

На уровне Core → Turret вводится отдельное действие `EMERGENCY_STOP`.

`EMERGENCY_STOP` не помещается в обычную FIFO и имеет более высокий приоритет.

При его обработке Turret Controller:

1. очищает очередь ожидающих обычных команд;
2. через HAL немедленно отправляет в STM32 стандартную UART-команду `STOP`.

На уровне HAL ↔ STM32 существует только одна физическая команда `STOP`.

Различие между обычным и аварийным STOP существует только на уровне Core ↔ Turret.

После аварийной остановки отдельное состояние блокировки, требующее ручного `RESET`, на этапе прототипа не вводится.

### Ограничение частоты UART

`Turret HAL` должен ограничивать частоту отправки команд в STM32, чтобы не перегружать последовательный интерфейс и микроконтроллер.

Для прототипа вводится настраиваемый минимальный интервал между последовательными UART-командами, например:

```text
uart_min_command_interval_ms
```

HAL не отправляет следующую обычную команду раньше разрешённого момента.

Конкретное значение интервала будет подобрано по baudrate, размеру пакета и результатам тестов на реальном STM32.

### Watchdog STM32

STM32 имеет собственный watchdog для команд скорости.

Если новая команда скорости не приходит в течение примерно `0.5` секунды, STM32 автоматически устанавливает:

```text
speed_x = 0
speed_y = 0
```

Этот watchdog является дополнительным уровнем защиты и не заменяет обычный или аварийный `STOP`.

## Контракты данных

Для взаимодействия модулей будут введены явные типы сообщений и данных.

Их точная структура пока не утверждена.

Проектирование контрактов будет выполнено отдельным этапом, тип за типом.
