# AGENTS.md — BelkaT4 / NavMin

Общие правила AI-assisted разработки проекта. Этот файл описывает **как работать с проектом** и не должен дублировать архитектурные контракты.

Если в затронутом поддереве есть более глубокий `AGENTS.md`, прочитай и его: локальные правила уточняют этот файл.

## 1. Базовый порядок работы

Перед изменением кода, тестов или документации:

1. Определи owner изменяемого поведения.
2. Найди нормативный документ/контракт.
3. Проверь, не существует ли уже нужная реализация или тест.
4. Определи минимальный scope изменения.
5. Реши, меняется ли только реализация или архитектурный контракт.

Не добавляй новые state/flag/queue/watchdog/ID/compatibility layer только «для надёжности», если задачу можно решить существующим контрактом или удалением лишнего механизма.

## 2. Источники истины

Не используй универсальное правило `code > docs` или `docs > code`.

- Архитектурные документы определяют, **как система должна быть устроена**.
- Код и тесты показывают, **что сейчас реализовано**.

Если они расходятся, не переписывай документацию автоматически под код. Сначала установи причину: implementation bug, неполная реализация, устаревший документ или новое архитектурное решение.

Основная карта документации:

```text
docs/dev/implementation-plan.md             порядок реализации и статус этапов (не архитектурный контракт)
docs/dev/architecture/overview.md         верхнеуровневая архитектура
docs/dev/architecture/contracts.md        общие межмодульные контракты
docs/dev/architecture/configuration.md    config schema / apply policy
docs/dev/architecture/serial-protocol.md  PC ↔ STM32 protocol
docs/dev/architecture/decisions.md        причины решений и отвергнутые варианты
docs/dev/architecture/problems.md         только открытые вопросы
docs/dev/modules/*                        ответственность конкретных модулей
docs/dev/diagrams/*.mmd                   source of truth диаграмм
```

PNG/SVG диаграммы — только экспорт.

Старые архивы, старые отчёты и memory не имеют приоритета над текущим working tree и актуальной архитектурой.

## 3. Что читать перед изменением

Не читай весь `docs/` без необходимости. Читай релевантные authoritative files.

- Core/Aiming: `overview.md`, `contracts.md`, `decisions.md`, `modules/core/*`, `core-diagram.mmd`.
- Vision/cameras/session: `overview.md`, `contracts.md`, `decisions.md`, `modules/vision/index.md`, `vision-diagram.mmd`.
- Turret/UART/STM32: `overview.md`, `contracts.md`, `configuration.md`, `serial-protocol.md`, `decisions.md`, `modules/turret/index.md`, `turret-diagram.mmd`.
- UI: `overview.md`, `contracts.md`, `decisions.md`, `modules/ui/index.md`, `ui-diagram.mmd`.
- Config: всегда `configuration.md` + owner module.
- Спорный/open вопрос: сначала `problems.md` и `decisions.md`.

Не проектируй заново уже закрытый вопрос только потому, что существует другая возможная архитектура.

При работе по master implementation plan сначала прочитай раздел текущего этапа в `docs/dev/implementation-plan.md`, затем перечисленные там authoritative документы.

## 4. Изменение кода

Перед реализацией:

- найди существующие API/contracts;
- не создавай параллельный путь без необходимости;
- найди связанные tests/helpers/fakes;
- делай минимальный runtime diff;
- не смешивай unrelated refactor с feature/fix без необходимости.

Если существующий код противоречит утверждённой архитектуре, не закрепляй drift как новый контракт без явного решения.

## 5. Тестирование — coverage first

Главное правило:

> Изменение production-кода само по себе не является причиной создавать новый тест.

Перед добавлением теста:

1. Сформулируй behavior/invariant, который нужно защитить.
2. Найди тесты по symbol/class/function.
3. Найди тесты по поведению, даже если они называются иначе.
4. Проверь существующие fixtures/fakes/helpers.
5. Предпочитай, в порядке приоритета:
   - не добавлять новый тест, если coverage уже достаточен;
   - расширить существующий тест;
   - добавить parameterized case;
   - добавить case в существующий тематический test file;
   - создать новый test/test file только для отдельного непокрытого failure mode или ответственности.

### Bug fix

```text
существующий test уже воспроизводит bug
→ новый regression test не нужен

существующий test почти покрывает boundary
→ расширить его

реального coverage нет
→ добавить минимальный regression test
```

По возможности regression test должен падать до fix.

### Дублирование

Два теста одного поведения оправданы только если ловят разные реальные классы отказов или проверяют разные значимые уровни.

Критерий:

> Если удалить один тест, потеряется ли отдельный failure mode?

Если нет — вероятно, это дубль.

### Hardware tests

Обычный suite не должен требовать камер, RTSP/physical video devices, UART/RS485, STM32 или физической турели. Hardware-dependent tests запускаются отдельно и должны быть явно отделены/маркированы, когда test tree появится.

Не утверждай, что тест прошёл, если он не запускался. Если проверка невозможна в текущем окружении, скажи об этом и дай пользователю локальную команду только если она действительно нужна.

### User-side validation

Если критерий завершения этапа зависит от окружения или оборудования, недоступного агенту, выдели отдельный user-side checkpoint. Такой checkpoint нужен только когда он проверяет реально недоступную агенту среду/устройство либо существенный local smoke; не заставляй пользователя бессмысленно повторять все проверки агента.

Перед выдачей команд пользователю сначала определи фактический project tooling и ОС. Не предполагай автоматически наличие `pip`, Poetry, Conda или другого менеджера. Для текущего проекта основной Python environment/package manager — **uv**, а пользователь по умолчанию работает на **Linux**. Поэтому предпочитай `uv` и Linux-команды, если конкретная задача явно не требует другого.

В handoff явно различай:

- проверки, реально выполненные агентом;
- обязательные проверки, которые остаётся выполнить на машине пользователя/железе.

Если обязательный критерий этапа зависит от user-side проверки, этап нельзя считать полностью принятым до получения её результата. Failure bootstrap окружения (`pip` отсутствует, пакет не установлен, устройство недоступно и т.п.) не объявляй автоматически failure тестируемого кода: сначала отдели проблему окружения от результата теста.

## 6. Когда менять документацию

Архитектурные документы обычно **не меняются** при изменении private helper, внутреннем rename, оптимизации или refactor без изменения responsibility/API/behavior.

Документацию нужно проверить/обновить, если меняется:

- межмодульный контракт;
- публичный type/API;
- ownership;
- state machine;
- threading/transport semantics;
- serial protocol;
- camera/session semantics;
- config field/apply policy;
- observable user behavior;
- архитектурное решение.

При изменении `docs/dev/architecture/` обязательно прочитай `docs/dev/architecture/AGENTS.md`.

## 7. Config и protocol

Config schema и wire protocol — контракты. Не меняй их только у одного producer/consumer.

При изменении:

1. найди owner и consumers;
2. обнови существующий contract coverage;
3. обнови нормативную документацию;
4. проверь migration/backward implications только если compatibility реально требуется;
5. не добавляй compatibility path автоматически.

## 8. Комментарии и стиль

Комментарии нужны для timing/concurrency/hardware/protocol/math/geometry и неочевидных invariants. Не комментируй очевидный код.

Новые имена файлов/каталогов — без пробелов; для Python предпочитай `snake_case`.

## 9. Git и локальные артефакты

Не создавай commit/tag автоматически без явной просьбы пользователя.

Основная рабочая ветка первой реализации — `feat/first-implementation`, пока пользователь явно не укажет другую.

### Commit cadence

Каждый завершённый Stage должен иметь как минимум один итоговый commit. Дополнительные commits внутри Stage допустимы только для самостоятельных, логически завершённых checkpoints, после которых repository остаётся в понятном и по возможности зелёном состоянии.

Не создавай commits только ради частоты. Избегай истории вида `wip`, `try fix`, `test2`, отдельных commits на каждый файл или каждое мелкое изменение. Если Stage небольшой и целостный, предпочитай один commit. Если Stage большой и естественно делится на несколько независимых проверяемых частей, допускаются несколько осмысленных commits.

Перед предложением `git add` / `git commit`:

1. проверь текущую ветку и working tree;
2. отдели изменения текущего Stage от ранее подготовленного baseline и unrelated files;
3. не используй `git add .`, если scope можно перечислить явно;
4. убедись, что обязательные проверки текущего checkpoint пройдены или явно отмечены как pending;
5. предложи конкретное commit message в формате `type(scope): short description`.

Stage-level commit не заменяет update master implementation plan: статус Stage меняет управляющий чат после приёмки результата.

Перед delivery проверяй фактический diff и не включай unrelated files.

После install/test/build/docs/package/codegen или другой команды, способной создать файлы, проверь working tree. Для user-side проверки по умолчанию достаточно:

```bash
git status --short
git status --short --ignored
git diff --check
```

Каждый новый артефакт классифицируй:

- **project/reproducibility artifact** → оставить и версионировать;
- **generated/local artifact** → он должен быть покрыт `.gitignore`;
- **непонятный артефакт** → не добавлять молча ни в Git, ни в `.gitignore`; сначала установить его назначение.

Не добавляй новое правило `.gitignore` только потому, что после запуска инструмента появился новый файл. Сначала проверь, не покрывается ли он уже существующим общим правилом и не является ли он значимым проектным артефактом. При сомнении можно проверить конкретный путь командой `git check-ignore -v <path>`.

Lockfiles не считать cache/generated junk автоматически. Для текущего Python/uv workflow `uv.lock` является reproducibility artifact и должен храниться в Git вместе с `pyproject.toml`.

## 10. Доставка файлов

Если задача изменила файлы и пользователь работает через browser chat, по умолчанию отдавай **overlay ZIP только с новыми и изменёнными проектными файлами**. Файлы внутри архива должны уже находиться в конечных относительных путях от project root, чтобы пользователь мог распаковать архив в корень проекта с заменой.

Не включай в обычный update ZIP неизменённые файлы или полный snapshot проекта. Полный архив проекта/документации отдавай только если пользователь явно попросил полный архив, если создаётся новый baseline/release/handoff snapshot или если полный snapshot действительно является результатом задачи.

Удаляемые файлы в overlay ZIP не включаются: перечисли их отдельно в финальном ответе и, когда полезно, дай готовую terminal-команду для удаления.

Не включай временные отчёты/helper scripts, если они не являются частью проекта и пользователь их не просил.

Перед выдачей ZIP проверь:

- заявленные created/changed files присутствуют;
- пути корректны;
- unrelated files отсутствуют;
- архив открывается;
- удаляемые файлы перечислены отдельно.

### Обязательный финальный формат после файловых изменений

Заканчивай ответ двумя короткими разделами.

```text
Действия пользователя:
- только реально необходимые действия;
- если нужны команды — ниже один copyable terminal block.
```

Если действий нет: `Действия пользователя: нет.`

```text
Файлы:
Архив: <final archive>

Добавить/заменить:
- ...

Удалить:
- ...
```

Если файлов не менялось, явно укажи это. Если файл нужно удалить, укажи его и текстом, и terminal-командой при необходимости: overlay ZIP сам удаление не выполняет.

## 11. Не делать

Не:

1. считать код автоматически более авторитетным, чем утверждённая архитектура;
2. переписывать архитектуру под implementation drift;
3. возвращать отвергнутый механизм без нового concrete requirement/failure case;
4. создавать тест только потому, что изменился production-код;
5. создавать новый test file до поиска существующего coverage;
6. дублировать fixtures/fakes/helpers без необходимости;
7. запускать hardware tests как часть обычного suite;
8. заявлять о проверке, которая не выполнялась;
9. менять unrelated files;
10. добавлять compatibility layer без требования совместимости;
11. дублировать архитектурные контракты в `AGENTS.md`;
12. использовать PNG/SVG как источник истины диаграммы;
13. создавать обязательные BIG/SMALL STAGE reports без запроса пользователя;
14. создавать commit/tag автоматически.
