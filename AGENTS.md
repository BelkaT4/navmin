# AGENTS.md — BelkaT4 / NavMin

Общие правила AI-assisted разработки проекта. Этот файл описывает **как работать с проектом** и не должен дублировать архитектурные контракты.

Если в затронутом поддереве есть более глубокий `AGENTS.md`, прочитай и его: локальные правила уточняют этот файл.

## 1. Базовый порядок работы

Перед изменением кода, тестов или документации:

1. Определи owner изменяемого поведения.
2. Найди нормативный документ/контракт.
3. Проверь, не существует ли уже нужная реализация или тест.
4. Определи минимальный scope изменения.
5. Реши, меняется ли только реализация или архитектурный контракт.

Не добавляй новые state/flag/queue/watchdog/ID/compatibility layer только «для надёжности», если задачу можно решить существующим контрактом или удалением лишнего механизма.

## 2. Источники истины

Не используй универсальное правило `code > docs` или `docs > code`.

- Архитектурные документы определяют, **как система должна быть устроена**.
- Код и тесты показывают, **что сейчас реализовано**.

Если они расходятся, не переписывай документацию автоматически под код. Сначала установи причину: implementation bug, неполная реализация, устаревший документ или новое архитектурное решение.

Основная карта документации:

```text
docs/dev/implementation-plan.md             порядок реализации и статус этапов (не архитектурный контракт)
docs/dev/architecture/overview.md         верхнеуровневая архитектура
docs/dev/architecture/contracts.md        общие межмодульные контракты
docs/dev/architecture/configuration.md    config schema / apply policy
docs/dev/architecture/serial-protocol.md  PC ↔ STM32 protocol
docs/dev/architecture/decisions.md        причины решений и отвергнутые варианты
docs/dev/architecture/problems.md         только открытые вопросы
docs/dev/modules/*                        ответственность конкретных модулей
docs/dev/diagrams/*.mmd                   source of truth диаграмм
```

PNG/SVG диаграммы — только экспорт.

Старые архивы, старые отчёты и memory не имеют приоритета над текущим working tree и актуальной архитектурой.

Если задача явно задаёт authoritative snapshot и SHA-256, сначала проверь hash и работай именно от этого snapshot. Не смешивай его с содержимым старых snapshot/handoff/archive; в handoff укажи фактически использованный baseline. После принятого commit следующий независимый checkpoint в manager-controlled workflow должен начинаться от свежего full snapshot, если состояние передаётся между чатами через архивы.

### Lifecycle implementation plans

Пока implementation plan крупной версии или инициативы активен, он является живым документом: отражает порядок реализации, зависимости, completion criteria и status.

После завершения соответствующего scope plan не удаляется и не превращается в бесконечный backlog: он получает явный `completed`-status (или эквивалентный однозначный marker) и сохраняется как historical/provenance document. Обычные bugfixes и небольшие новые features задним числом в завершённый plan не добавляются. Для новой крупной инициативы при необходимости создавай новый отдельный plan; конкретную структуру каталогов заранее не фиксируй.

## 3. Что читать перед изменением

Не читай весь `docs/` без необходимости. Читай релевантные authoritative files.

- Core/Aiming: `overview.md`, `contracts.md`, `decisions.md`, `modules/core/*`, `core-diagram.mmd`.
- Vision/cameras/session: `overview.md`, `contracts.md`, `decisions.md`, `modules/vision/index.md`, `vision-diagram.mmd`.
- Turret/UART/STM32: `overview.md`, `contracts.md`, `configuration.md`, `serial-protocol.md`, `decisions.md`, `modules/turret/index.md`, `turret-diagram.mmd`.
- UI: `overview.md`, `contracts.md`, `decisions.md`, `modules/ui/index.md`, `ui-diagram.mmd`.
- Config: всегда `configuration.md` + owner module.
- Спорный/open вопрос: сначала `problems.md` и `decisions.md`.

Не проектируй заново уже закрытый вопрос только потому, что существует другая возможная архитектура.

При работе по master implementation plan сначала прочитай раздел текущего этапа в `docs/dev/implementation-plan.md`, затем перечисленные там authoritative документы.

## 4. Изменение кода

Перед реализацией:

- найди существующие API/contracts;
- не создавай параллельный путь без необходимости;
- найди связанные tests/helpers/fakes;
- делай минимальный runtime diff;
- не смешивай unrelated refactor с feature/fix без необходимости.

Если существующий код противоречит утверждённой архитектуре, не закрепляй drift как новый контракт без явного решения.

## 5. Тестирование — coverage first

Главное правило:

> Изменение production-кода само по себе не является причиной создавать новый тест.

Перед добавлением теста:

1. Сформулируй behavior/invariant, который нужно защитить.
2. Найди тесты по symbol/class/function.
3. Найди тесты по поведению, даже если они называются иначе.
4. Проверь существующие fixtures/fakes/helpers.
5. Предпочитай, в порядке приоритета:
   - не добавлять новый тест, если coverage уже достаточен;
   - расширить существующий тест;
   - добавить parameterized case;
   - добавить case в существующий тематический test file;
   - создать новый test/test file только для отдельного непокрытого failure mode или ответственности.

### Bug fix

```text
существующий test уже воспроизводит bug
→ новый regression test не нужен

существующий test почти покрывает boundary
→ расширить его

реального coverage нет
→ добавить минимальный regression test
```

По возможности regression test должен падать до fix.

### Дублирование

Два теста одного поведения оправданы только если ловят разные реальные классы отказов или проверяют разные значимые уровни.

Критерий:

> Если удалить один тест, потеряется ли отдельный failure mode?

Если нет — вероятно, это дубль.

### Hardware tests

Обычный suite не должен требовать камер, RTSP/physical video devices, UART/RS485, STM32 или физической турели. Hardware-dependent tests запускаются отдельно и должны быть явно отделены/маркированы, когда test tree появится.

Не утверждай, что тест прошёл, если он не запускался. Если проверка невозможна в текущем окружении, скажи об этом и дай пользователю локальную команду только если она действительно нужна.

### User-side validation

Если критерий завершения этапа зависит от окружения или оборудования, недоступного агенту, выдели отдельный user-side checkpoint. Такой checkpoint нужен только когда он проверяет реально недоступную агенту среду/устройство либо существенный local smoke; не заставляй пользователя бессмысленно повторять все проверки агента.

Перед выдачей команд пользователю сначала определи фактический project tooling и ОС. Не предполагай автоматически наличие `pip`, Poetry, Conda или другого менеджера. Для текущего проекта основной Python environment/package manager — **uv**, а пользователь по умолчанию работает на **Linux**. Поэтому предпочитай `uv` и Linux-команды, если конкретная задача явно не требует другого.

В handoff явно различай:

- проверки, реально выполненные агентом;
- обязательные проверки, которые остаётся выполнить на машине пользователя/железе.

Если обязательный критерий этапа зависит от user-side проверки, этап нельзя считать полностью принятым до получения её результата. Failure bootstrap окружения (`pip` отсутствует, пакет не установлен, устройство недоступно и т.п.) не объявляй автоматически failure тестируемого кода: сначала отдели проблему окружения от результата теста.

Если manager-controlled prompt явно оставляет Ruff для user-side validation, рабочий чат Ruff не запускает и пишет в handoff точно: `Ruff: NOT RUN — user-side validation required.` Не добивайся зелёного lint через новые `noqa`, `ignore`, `per-file-ignore`, сокращение lint selection, Ruff preview или изменение formatter/lint policy без отдельного осознанного решения. `--unsafe-fixes` без явного разрешения не использовать. Это не глобальный запрет Ruff: в других задачах запускай его, когда этого требует task/tooling.

## 6. Когда менять документацию

Архитектурные документы обычно **не меняются** при изменении private helper, внутреннем rename, оптимизации или refactor без изменения responsibility/API/behavior.

Документацию нужно проверить/обновить, если меняется:

- межмодульный контракт;
- публичный type/API;
- ownership;
- state machine;
- threading/transport semantics;
- serial protocol;
- camera/session semantics;
- config field/apply policy;
- observable user behavior;
- архитектурное решение.

При изменении `docs/dev/architecture/` обязательно прочитай `docs/dev/architecture/AGENTS.md`.

## 7. Config и protocol

Config schema и wire protocol — контракты. Не меняй их только у одного producer/consumer.

При изменении:

1. найди owner и consumers;
2. обнови существующий contract coverage;
3. обнови нормативную документацию;
4. проверь migration/backward implications только если compatibility реально требуется;
5. не добавляй compatibility path автоматически.

## 8. Комментарии и стиль

Комментарии нужны для timing/concurrency/hardware/protocol/math/geometry и неочевидных invariants. Не комментируй очевидный код.

Новые имена файлов/каталогов — без пробелов; для Python предпочитай `snake_case`.

## 9. Cross-chat ownership и независимый аудит

Проект может выполняться несколькими специализированными чатами, но их роли различаются.

### Рабочий чат этапа

Рабочий чат:

- реализует только свой Stage/scope;
- создаёт и изменяет project files;
- запускает все доступные ему проверки;
- может запросить у пользователя промежуточный local/hardware check, если без результата нельзя корректно продолжить реализацию;
- в финальном handoff перечисляет реально выполненные проверки, remaining user-side checks, deviations и open issues;
- может предложить естественные commit boundaries и commit messages.

По умолчанию рабочий чат **не**:

- меняет статус Stage в master implementation plan;
- объявляет Stage принятым;
- создаёт финальный commit/tag;
- самостоятельно решает, что требуется отдельный независимый audit.

Исключение допустимо только если пользователь явно делегировал эти полномочия конкретному чату.

### Управляющий чат

Управляющий чат владеет:

- master implementation plan и статусами Stage;
- финальной приёмкой результата рабочего чата;
- повторными/дополнительными проверками;
- координацией финальных user-side/hardware checks;
- решением о необходимости независимого аудита;
- финальными `git add` / `git commit` командами после приёмки;
- архитектурными решениями, которые выходят за implementation-level choices рабочего Stage.

Stage commit означает **принятый checkpoint**, а не просто окончание написания кода. При этом acceptance промежуточного/prototype/minimum scoped checkpoint не означает автоматически завершение всего Stage: `done` допустим только после проверки полных completion criteria активного authoritative implementation plan.

### Независимый аудит

Независимый аудит не обязателен после каждого Stage. Его необходимость определяет управляющий чат по реальному риску изменения.

Аудит особенно уместен, если изменение затрагивает критические protocol/state-machine/concurrency/hardware-safety boundaries, несколько модулей сразу, recovery/error semantics или финальную интеграцию.

Рабочий чат не должен автоматически требовать отдельный audit только потому, что Stage большой.

Для действительно независимого аудита по умолчанию создавай **новый audit chat с актуальным snapshot и узким audit scope**. Старый audit chat используй только для продолжения того же аудита или разбора его прежних замечаний.

Audit chat не должен самостоятельно перепроектировать утверждённую архитектуру. Если найден настоящий архитектурный конфликт, он описывается и возвращается управляющему чату для решения.

Независимый audit по умолчанию **read-only**, если задача явно не поручает fixes: он не меняет production, tests, docs или Stage status. Нормальный flow — `audit findings → manager triage → отдельный targeted fix`, когда fix действительно нужен.

## 10. Git и локальные артефакты

Не создавай commit/tag автоматически без явной просьбы пользователя.

### Рабочий процесс через task branch и Pull Request

`main` — стабильная интеграционная ветка. Обычные изменения кода, тестов и документации напрямую в `main` не вносятся и напрямую туда не публикуются. Каждая логическая задача выполняется в отдельной короткоживущей task branch от актуального `main` и попадает в `main` только через Pull Request.

Перед началом новой задачи по умолчанию:

```bash
git switch main
git pull --ff-only
git switch -c <type>/<task-name>
```

Правила:

- одна ветка = одна логическая задача; не смешивай unrelated изменения;
- не используй локальный `git merge <feature> -> main` как обычный способ интеграции;
- implementation/docs/fix commits создаются только в task branch;
- task branch публикуется в `origin`, после чего создаётся Pull Request в `main`;
- перед merge проверь diff Pull Request, обязательные проверки и конфликты с изменениями других участников;
- если `origin/main` изменился после создания task branch, сначала осознанно синхронизируй task branch с актуальным `main`, разреши конфликты и повтори релевантные проверки; не переписывай уже опубликованную общую историю без отдельной причины;
- merge в `main` выполняется через Pull Request; способ merge определяется текущими правилами репозитория/команды;
- после merge обнови локальный `main` через `git switch main` + `git pull --ff-only` перед следующей задачей;
- tags/releases — отдельное управляемое действие и не создаются автоматически как часть обычного feature/fix/docs Pull Request.

Не вводи заранее тяжёлый GitFlow, `develop`, release branches или обязательные issue IDs, пока реальный workflow команды этого не требует.

### Именование веток

Используй lowercase kebab-case и префикс по назначению:

```text
feat/<name>
fix/<name>
docs/<name>
refactor/<name>
test/<name>
chore/<name>
experiment/<name>
```

Примеры:

```text
feat/first-implementation
feat/stereo-distance
fix/serial-recovery
docs/architecture
refactor/vision-pipeline
experiment/new-tracker
```

Не создавай долгоживущие персональные ветки разработчиков без отдельной причины.

### Именование commits

Используй формат:

```text
type(scope): short description
```

Основные `type`:

```text
feat
fix
docs
refactor
test
chore
build
```

Commit message пиши на английском, коротко и по результату изменения, а не по процессу работы. Такое сообщение должно оставаться понятным из repository history без знания временной схемы управляющего чата. Не используй внутренние checkpoint/audit labels вроде `PRE-E2E`, `E2E-1` или `audit-fix`, если такой термин сам не является устойчивой частью versioned project documentation.

Хорошие примеры:

```text
feat(foundation): implement stage 1 runtime foundation
docs(diagrams): improve overview diagram layout
fix(serial): reject mismatched response command
test(turret): cover emergency retry boundary
```

Избегай сообщений вроде:

```text
update files
stage 2 work
fix stuff
try again
final version
```

Используй естественный `scope` по смысловой области проекта, например `foundation`, `config`, `vision`, `core`, `aiming`, `turret`, `serial`, `firmware`, `ui`, `integration`, `diagrams`, `architecture`, `project`.

Финальный Stage commit должен описывать реализованный результат, а не только номер Stage. Например `feat(config): implement configuration and calibration foundation` предпочтительнее `feat(stage2): complete stage 2`.


### Commit cadence

Каждый завершённый Stage должен иметь как минимум один итоговый commit. Дополнительные commits внутри Stage допустимы только для самостоятельных, логически завершённых checkpoints, после которых repository остаётся в понятном и по возможности зелёном состоянии.

Не создавай commits только ради частоты. Избегай истории вида `wip`, `try fix`, `test2`, отдельных commits на каждый файл или каждое мелкое изменение. Если Stage небольшой и целостный, предпочитай один commit. Если Stage большой и естественно делится на несколько независимых проверяемых частей, допускаются несколько осмысленных commits.

Перед предложением `git add` / `git commit`:

1. проверь текущую ветку и working tree;
2. отдели изменения текущего Stage от ранее подготовленного baseline и unrelated files;
3. не используй `git add .`, если scope можно перечислить явно;
4. убедись, что обязательные проверки текущего checkpoint пройдены или явно отмечены как pending;
5. предложи конкретное commit message в формате `type(scope): short description`.

Stage-level commit не заменяет update master implementation plan: статус Stage меняет управляющий чат после приёмки результата.

### Переписывание истории

Amend последнего локального commit допустим для только что обнаруженной ошибки или неудачного сообщения. Более старую уже принятую историю по умолчанию не переписывай только ради косметики: смена commit SHA ломает полезный provenance из snapshots, audit reports и handoff. Если history rewrite действительно нужен, выполняй его как отдельное осознанное действие пользователя/manager; interactive rebase не запрещён сам по себе.

Перед delivery проверяй фактический diff и не включай unrelated files.

После install/test/build/docs/package/codegen или другой команды, способной создать файлы, проверь working tree. Для user-side проверки по умолчанию достаточно:

```bash
git status --short
git status --short --ignored
git diff --check
```

Каждый новый артефакт классифицируй:

- **project/reproducibility artifact** → оставить и версионировать;
- **generated/local artifact** → он должен быть покрыт `.gitignore`;
- **непонятный артефакт** → не добавлять молча ни в Git, ни в `.gitignore`; сначала установить его назначение.

Не добавляй новое правило `.gitignore` только потому, что после запуска инструмента появился новый файл. Сначала проверь, не покрывается ли он уже существующим общим правилом и не является ли он значимым проектным артефактом. При сомнении можно проверить конкретный путь командой `git check-ignore -v <path>`.

Lockfiles не считать cache/generated junk автоматически. Для текущего Python/uv workflow `uv.lock` является reproducibility artifact и должен храниться в Git вместе с `pyproject.toml`.

## 11. Доставка файлов

Если задача изменила файлы и пользователь работает через browser chat, по умолчанию отдавай **overlay ZIP только с новыми и изменёнными проектными файлами**. Файлы внутри архива должны уже находиться в конечных относительных путях от project root, чтобы пользователь мог распаковать архив в корень проекта с заменой.

Не включай в обычный update ZIP неизменённые файлы или полный snapshot проекта. Полный архив проекта/документации отдавай только если пользователь явно попросил полный архив, если создаётся новый baseline/release/handoff snapshot или если полный snapshot действительно является результатом задачи.

Удаляемые файлы в overlay ZIP не включаются: перечисли их отдельно в финальном ответе и, когда полезно, дай готовую terminal-команду для удаления.

Не включай временные отчёты/helper scripts, если они не являются частью проекта и пользователь их не просил.

Перед выдачей ZIP проверь:

- заявленные created/changed files присутствуют;
- пути корректны;
- unrelated files отсутствуют;
- архив открывается;
- удаляемые файлы перечислены отдельно.

Overlay ZIP, full snapshot и другой handoff-архив — только способ передачи файлов/состояния. Они не заменяют Git/PR workflow и не дают оснований применять изменения напрямую в `main`: изменения должны применяться в соответствующей task branch, проверяться, фиксироваться там и интегрироваться через Pull Request.

### Обязательный финальный формат после файловых изменений

Заканчивай ответ двумя короткими разделами.

```text
Действия пользователя:
- только реально необходимые действия;
- если нужны команды — ниже один copyable terminal block.
```

Если действий нет: `Действия пользователя: нет.`

```text
Файлы:
Архив: <final archive>

Добавить/заменить:
- ...

Удалить:
- ...
```

Если файлов не менялось, явно укажи это. Если файл нужно удалить, укажи его и текстом, и terminal-командой при необходимости: overlay ZIP сам удаление не выполняет.

## 12. Язык и терминология документации

Документация проекта ведётся на русском языке. Текст должен быть простым, точным и понятным без лишнего смешения русского и английского.

Общие правила:

- обычную прозу пиши естественным русским языком;
- не оставляй английское слово только потому, что оно привычно в разработке, если существует ясный и точный русский вариант;
- не используй гибридные формы вроде `reset'ит`, `clamp'ит`, `refresh'ит`, `cache'ится`, `ping'ует` и аналогичные;
- не усложняй текст канцелярскими или чрезмерно архитектурными формулировками, если ту же мысль можно выразить проще;
- не переводи точные технические идентификаторы:
  - имена классов, функций и методов;
  - config keys и enum values;
  - команды и CLI-флаги;
  - имена файлов и каталогов;
  - protocol/state names;
  - точные статусы и значения вроде `PASS`, `WARN`, `FAIL`, `ONLINE`, `MOTOR_OFF`;
  - официальные названия профилей `VIRTUAL`, `STM32`, `CAMERAS`, `REAL`;
- устоявшийся технический термин можно оставить на английском, если русский перевод ухудшает точность или затрудняет сопоставление с кодом и внешней документацией;
- если английский рабочий термин важен, но может быть непонятен читателю, при первом употреблении дай короткое русское пояснение;
- не объясняй очевидные общеупотребительные понятия только ради наличия определения;
- пользовательская документация должна быть максимально понятной человеку, который эксплуатирует систему, и использовать русский язык везде, где это не мешает точности;
- developer documentation может сохранять больше технических терминов, но обычная проза всё равно должна оставаться преимущественно русской и читаемой.

Для сквозных специальных терминов проекта допускается отдельный `docs/dev/terminology.md`.

В общий словарь включай только термины, которые:

- встречаются в нескольких частях проекта;
- имеют специальное значение именно в контексте NavMin;
- без пояснения могут быть поняты неправильно.

Не превращай словарь в переводчик очевидных английских слов или идентификаторов.

Узкоспециализированный термин, относящийся только к одному модулю или процедуре, лучше кратко объяснить непосредственно в профильном документе.

Если термин используется и в пользовательской, и в разработческой документации, наличие определения в общем словаре не отменяет краткого пояснения на месте, когда без него оператору или новому разработчику будет трудно понять инструкцию.

При языковой чистке нельзя механически заменять одинаковое английское слово одним русским эквивалентом во всех местах. Формулировка выбирается по смыслу конкретного предложения.

Любая языковая правка, которая способна изменить технический смысл, границу ответственности, safety-утверждение, current/target status или нормативный contract, считается смысловой правкой и должна проходить обычное согласование перед изменением документа.

## 13. Операторские инструкции и runbook

Операторские инструкции и runbook-документы должны оставаться практическими процедурами, а не превращаться в объединённый источник архитектуры, истории проекта и roadmap.

Для таких документов действует правило:

```text
подготовить
→ проверить готовность
→ запустить
→ выполнить контролируемую проверку
→ при необходимости остановиться
→ штатно завершить
→ сохранить результаты
```

В runbook следует оставлять:

- точные команды и порядок действий оператора;
- предварительные проверки и условия перехода к следующему этапу;
- актуальные ограничения безопасности;
- критерии остановки проверки;
- порядок штатного завершения;
- перечень материалов, которые нужно сохранить после запуска;
- небольшие практические пояснения конфигурации, без которых оператор не сможет выполнить процедуру.

В runbook не следует дублировать:

- историю предыдущих испытаний и хронологию разработки;
- текущий статус этапов проекта;
- roadmap и будущие implementation checkpoints;
- полный реестр открытых технических проблем;
- подробное описание архитектуры;
- полный справочник конфигурации;
- внутренние подробности реализации firmware/runtime, если они не влияют непосредственно на действия оператора.

Для такой информации ссылайся на соответствующий нормативный источник:

- status, этапы и дальнейшая работа → `implementation-plan.md`;
- открытые технические проблемы → `problems.md`;
- схема и правила конфигурации → `configuration.md`;
- причины архитектурных решений → `decisions.md`;
- подробности реализации STM32 → `firmware/stm32/README.md` и профильная архитектурная документация.

Если информация влияет на безопасность оператора, в runbook должно оставаться краткое актуальное ограничение, даже если подробное объяснение находится в другом документе.

Не сохраняй в runbook историческое наблюдение только потому, что оно когда-то было важным. Исторический факт должен оставаться там только тогда, когда без него невозможно правильно выполнить текущую процедуру.

Не описывай непроверенную аппаратную функцию как обычный шаг процедуры. Если для проверки `Emergency`, `MOTOR_OFF`, отказа связи или другого safety-critical поведения ещё нет отдельного безопасного способа проведения теста, runbook не должен предлагать оператору самостоятельно создавать такой отказ.

Программная проверка, эмуляция, localhost/PTY-тест или `PREFLIGHT PASS` не являются доказательством работы физического оборудования и не должны описываться как такое доказательство.

Если runbook начинает повторять большие фрагменты другого нормативного документа, оставь краткое практическое правило и ссылку на источник истины вместо копирования подробностей.

## 14. Не делать

Не:

1. считать код автоматически более авторитетным, чем утверждённая архитектура;
2. переписывать архитектуру под implementation drift;
3. возвращать отвергнутый механизм без нового concrete requirement/failure case;
4. создавать тест только потому, что изменился production-код;
5. создавать новый test file до поиска существующего coverage;
6. дублировать fixtures/fakes/helpers без необходимости;
7. запускать hardware tests как часть обычного suite;
8. заявлять о проверке, которая не выполнялась;
9. менять unrelated files;
10. добавлять compatibility layer без требования совместимости;
11. дублировать архитектурные контракты в `AGENTS.md`;
12. использовать PNG/SVG как источник истины диаграммы;
13. создавать обязательные BIG/SMALL STAGE reports без запроса пользователя;
14. создавать commit/tag автоматически;
15. считать независимый audit обязательным после каждого Stage;
16. позволять рабочему чату молча менять master-plan status или принимать архитектурные решения за пределами своего scope;
17. использовать старый audit chat как универсального аудитора несвязанных новых задач по умолчанию;
18. вносить обычные рабочие изменения или публиковать commits напрямую в `main`;
19. обходить Pull Request workflow через локальный merge, overlay ZIP, snapshot или другой handoff-механизм.
